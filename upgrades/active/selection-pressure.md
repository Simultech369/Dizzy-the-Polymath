# Selection Pressure

**Status**: Active operating lens, not runtime doctrine.

## Purpose

Dizzy should evolve from experience without preserving every residue of experience. PBMRebate / Pharmacy Fiduciary Commons should expose extraction without becoming dependent on the complexity it criticizes.

Use this note to force subtraction, simplification, and incentive clarity before adding another layer.

## Rule

Before adopting a major upgrade, answer:

1. What does this reduce?
2. What failure has actually occurred that justifies it?
3. Could a simpler boundary prevent most of that failure?
4. Does this increase capability or dependence?
5. What should become less necessary if this succeeds?

If the answer is mostly "it adds nuance," keep the idea in `upgrades/provenance/` until experience earns it.

## Capability Chokepoint Pass

Use before adopting a new capability, dependency, workflow layer, memory path, external service, dashboard, public surface, or automation.

1. What can Simul do afterward with less dependency than before? (Avoid the blind spot where a feature increases capability short-term but creates long-term dependency.)
2. Who can inspect it?
3. Who can revoke, exit, or route around it?
4. What chokepoint might this create?

## Dizzy Questions

Use for memory, routing, doctrine, trust zones, public surfaces, and prompt architecture.

- **Capability**: Does this make Simul more capable, or more dependent on Dizzy?
- **Judgment**: Does this preserve judgment, or preserve residue?
- **Boundary**: Can the trust-zone distinction survive fatigue and imperfect recall?
- **Compression**: Does this reduce future explanation burden?
- **Failure containment**: If the model/provider/operator fails, what remains bounded?
- **Self-obsolescence**: What repeated task should become easier, shorter, or unnecessary?

## PBMRebate / PFC Questions

Use before importing lessons from the pharmaceutical project back into Dizzy, and before presenting PBMRebate as structurally anti-extractive.

- **Simplification**: Does this reduce rebate complexity, or monetize navigation through it?
- **Exit power**: Who gains a credible alternative or bargaining path?
- **Chokepoints**: Does this dissolve a chokepoint, move it, or create a new one?
- **Contestability**: Who can challenge claims, amounts, governance decisions, and omissions?
- **Beneficiary conflict**: Are the user, buyer, and beneficiary the same party? If not, what conflict emerges?
- **Founder/council disappearance**: What still works if the operator disappears, sells, pivots, or is captured?

## Subtraction Sprint

For one cycle, default to reduction:

1. Pick a proposed feature, doctrine note, or mechanism.
2. Name the concrete failure it prevents.
3. Remove ceremony that does not change runtime behavior, governance accountability, user capability, or economic incentives.
4. Prefer one visible boundary over three hidden distinctions.
5. Preserve only the part that improves judgment under worse conditions.

## Hard Pushback

The strongest versions of these projects may require refusing some beautiful distinctions.

Some tensions should become code.
Some should become product choices.
Some should remain open.
Some should be killed.
